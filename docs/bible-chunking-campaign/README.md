## What this is

This repository (`logos-scripture-graph`) is an open-source build of a Bible
knowledge graph. One part of that build is a **chunking campaign**: every book of
the Bible is divided into candidate *units of meaning* (a narrative scene, a
speech, a psalm, a legal procedure, an oracle, and so on), and every decision is
recorded: where the boundary was drawn, why, which alternative was rejected, how
confident the reviewers were, and what evidence they cited.

The campaign is a **research and testing run** that feeds a later, separate
final project. Its outputs are *candidates*. The chunk records are
machine-labelled `non_authorizing: true` and `candidate_only: true`; presence in
this campaign grants no promotion into any canonical graph, atlas, or gold set.
(Source: `M8_PUBLIC_TRANSPARENCY_README.md` and `m8_public_release_manifest.yaml`,
linked below.)

All campaign working files live under
`.ai/scratch/multi_model_bible_chunking/` (the "scratch" area, which is
deliberately separate from canonical data).

## The lines of work

Several independent attempts to chunk the whole Bible live side by side. They are
kept apart on purpose, so that agreement between them means something.

- **The fork.** `.ai/scratch/multi_model_bible_chunking/FORK_README.md` describes
  the original idea: several AI models each chunk the entire Bible independently,
  in separate folders, from the same shared research baseline, and the outputs are
  compared later. Agreement marks easy chunks; disagreement marks where careful
  work should focus. Slots M1 through M8 are listed in the fork's `manifest.yaml`.
  No model may read another model's map before it is complete, and there is no
  real-time comparison (`comparison/README.md`).
- **M7 (`M7_sol`).** An earlier, complete line. Per `.ai/control/PROJECT_STATUS.md`
  (entry T543), its first pass covered 66 of 66 books (2,659 merged literary
  chunks) and was candidate-only. A per-book corrective re-review followed
  (entries T544 onward). That record notes its roles were all one model family
  ("same-model role separation is not cross-model convergence"). UNCONFIRMED: the
  exact current state of the M7 re-review beyond the entries read for this page.
- **M8 (`M8_fable`).** The current, in-progress line, and the subject of the
  status table above. It is an orchestrated mesh of AI sub-agents (writers,
  blind reviewers, adjudicators) working one book at a time under a written method
  (`BIBLE_CHUNKING_METHOD.v6.md`) and a per-book close gate. M8 was set up as a
  second provider relative to M7 so the two can later be compared
  (`model_manifest.yaml`: "a second provider relative to the OpenAI/Codex M7_sol
  mesh").
- **Convergence.** In this campaign, "convergence" means comparing independent
  generations or lanes to see **where they agree and where they disagree**. The
  agreement is treated as a weak signal, and the disagreement is treated as the
  more useful signal, so it is preserved rather than averaged away. The planned
  M7/M8 comparison (task T521; see
  `docs/governance/T521_EXTERNAL_CONVERGENCE_HANDOFF_PROMPT.md`) is a separate,
  later, gated step. Per the public checkpoint, it had **not** been run at that
  time. UNCONFIRMED: whether it has begun since.
- **Blind lanes inside M8.** Within a book, M8 uses two (sometimes three) review
  lanes that cannot see each other's output ("blind lanes"), with different lenses
  and reading orders. A single review lane is banned; two blind lanes are the
  minimum (`BIBLE_CHUNKING_METHOD.v6.md`, section 19). Lanes that share one model
  count as one voice, not independent confirmation.
- **A/B/C.** In this repository, "A/B/C" is confirmed in one place only:
  `docs/chunking/EXECUTION_PLAN.md` (variants A, B and C of an early
  sentence-safe chunk-size comparison: genre-aware default budgets, genre-aware
  tight budgets, and a naive sentence-window baseline). The separate
  "habitat overlay" review and its A/B round-02 convergence cross-audits are
  **UNCONFIRMED here**: no definition of them was found in this worktree, so this
  page does not describe them. If they are part of this campaign, the owner
  should supply the source files.

## Transparency

### How decisions are recorded

Under `.ai/scratch/multi_model_bible_chunking/M8_fable/`:

| What | Where |
|---|---|
| Candidate chunk per book, each with `boundary_rationale`, `strongest_rejected_alternative`, `boundary_evidence_refs`, `confidence`, `review_status`, `decision_id` | `book_chunks/<Book>/chunks.jsonl`; flat map in `whole_bible_chunk_map.jsonl` |
| Strategy written before chunking a book | `book_strategy/<Book>.md` |
| Review packets, decision relations, appeals, superseded decisions | `reviews/<Book>/` |
| Per-book close receipt with hash pins and audit counters | `receipts/<Book>_completion.json` |
| Working substrate for recent books (briefs, lanes, repairs) | `sp_durable/<Book>/` |
| The written method, versioned (never overwritten) | `BIBLE_CHUNKING_METHOD.v1.md` through `v6.md` |
| The close gate every book must pass | `CAMPAIGN_CLOSE_GATE.v1.md` |
| Proposed method changes | `method_change_proposals.v1.jsonl` |

Superseded decisions are kept next to their replacements rather than deleted.

### Where high-risk and low-confidence items are registered

- `low_confidence_register.jsonl`: decisions the campaign does not stand behind
  strongly, with why and the possible downstream risk.
- `frontier_escalation_queue.jsonl`: items escalated for a stronger reviewer.
- `atlas_candidate_feed.jsonl`: feed for the difficulty/risk atlas. The atlas
  separates what was measured (did blind lanes disagree), what depends on a
  passage (its **blast radius**: one unit versus a whole book or the campaign),
  and what was merely judged (`BIBLE_CHUNKING_METHOD.v6.md`, section 15). The
  feed carries no promotion authority.
- `ERROR_PATTERN_LEDGER.v1.md` (with machine rows in
  `error_pattern_ledger.v1.jsonl`): every defect class that reviewers caught, its
  root cause, and where to re-scan. The campaign's own mistakes are logged here,
  not scrubbed. A re-scan flag is a review trigger, not a verdict.
- Per-book review receipts: `receipts/<Book>_completion.json` and
  `reviews/<Book>/`.

### Evidence-tier labels

Substantive claims in the campaign's records are meant to name how they are known,
and never a stronger tier than is true (`CAMPAIGN_CLOSE_GATE.v1.md`, item 24;
`BIBLE_CHUNKING_METHOD.v6.md`, section 18). The tiers, strongest first:

MEASURED, EXTRACTED, TRANSCRIBED, REPORTED, INFERRED, ASSUMED, UNAVAILABLE.

UNAVAILABLE is a value, not a blank. Corroboration does not upgrade a tier.

### Known limitations

- **Candidate-only.** No human, editor, or external body has ratified any
  boundary. `review_status: candidate_review_complete` means the campaign's own
  review mesh finished its pass.
- **Not independent of itself.** All M8 sub-agents are Anthropic-family models.
  Agreement inside M8 is corroboration, never cross-provider evidence
  (`model_manifest.yaml`).
- **Mixed method versions.** Books were closed under different mesh revisions and
  method versions, so the method is not uniform across all closed books
  (public checkpoint, "Known gaps").
- **Missing review packets.** A known campaign-level gap (error-ledger entry
  E-57, `CAMPAIGN_CLOSE_GATE.v1.md`, OW-29 addendum): closes from Job onward do
  not write `reviews/<book>/review_packets.jsonl`, so the full review-coverage
  validator fails for those books. This is a retention and layout gap that has
  not been fixed; exact verse coverage is validated separately.
- **Open audit.** The Ezekiel receipt records its transcript audit as owed and not
  met (`receipts/Ezek_completion.json`, field `transcript_audit`).
- **Working files record local paths.** Some files (for example
  `model_manifest.yaml`) contain absolute local workstation paths.
- **Versification.** English (WEB) and Hebrew (MT) verse numbering differ in places;
  receipts record such zones where a book has them.
- **Scope so far.** The New Testament is gated behind an owner gate for Greek
  witnesses (`OWNER_GATE_NT_GREEK_PREFLIGHT.v1.md`) and no New Testament M8
  chunking exists.

### AI-model disclosure

This campaign is run by AI models, orchestrated by AI, with a human owner who sets
the rules and decides. There has been **no human scholarly review** of the chunk
decisions.

The M8 mesh was designed with a model ladder in which a stronger reviewer model
adjudicates (`model_manifest.yaml`). That designated reviewer model was not
available, and an owner ruling (OW-25, recorded in `ERROR_PATTERN_LEDGER.v1.md`)
made **every role currently run on `claude-opus-5-5`**, including the review
roles. This is recorded in the receipt as a `grader_fallback`: the author and the
grader share one set of weights, so their agreement is weaker evidence than
agreement between different models. A review of each book by the designated
reviewer model is **deferred to the end of the campaign (OW-28) and has not been
done.** The Ezekiel receipt carries these fields (`grader_fallback`,
`fable_end_review`: deferred). UNCONFIRMED: whether the receipts of books closed
before OW-25 record their model roles in the same way; only the Ezekiel receipt
was found to carry those fields.

## Invitation to scholars and readers

Academic review, corrections, and improvements are welcome. If you find a
boundary you think is wrong, a source citation that does not hold, a missing
caveat, or a better way to organize the records, please open an issue at
<https://github.com/lowelltwong-alt/logos-scripture-graph/issues> (the repository
named in `m8_public_release_manifest.yaml`), naming the book, the span (for
example `Ezek.37.1-Ezek.37.14`), the file, and your evidence. Changes land by pull
request; see [`CONTRIBUTING.md`](../../CONTRIBUTING.md). Disagreement from
reviewers is useful here: the campaign is designed to preserve it.

## After each book closes

1. Run `python -B docs/bible-chunking-campaign/refresh_campaign_status.py`. It
   rewrites only the block between the `BOOK_STATUS` markers above and prints a
   one-line summary (it refuses to run if the markers are missing).
2. Review the diff of `docs/bible-chunking-campaign/README.md`. The changes
   should be limited to the status block; check any consistency warning it prints.
3. The owner's orchestrator commits, pushes, opens the pull request, and merges.
   The script itself runs no git commands.
