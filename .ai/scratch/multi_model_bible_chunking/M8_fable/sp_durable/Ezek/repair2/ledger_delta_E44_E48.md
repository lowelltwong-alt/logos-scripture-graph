
## E-44 (2026-09-21) - A GENERATOR EXTENDED IN PLACE DESTROYED THE POSITION IT HAD PRODUCED

The scholar-record generator was extended from v1 behaviour to v2 behaviour by editing the same file. The v2 output is checked and passes; the v1 output sits beside it, on disk, **no longer reproducible from anything**, because the bytes that made it are gone. Nothing failed, which is why it went unnoticed: a passing check on the new version says nothing about the old one. Worse, the file is named `gen_scholar_record.py` - an UNVERSIONED name emitting a versioned artifact, so the name itself cannot record which position it holds. Cure, now in method record v6 section 10 and obligation 13: **copy a shipped generator aside before extending it and re-issue as vN+1**, and name a generator for the version it produces. A missing generator is a FAILED check, never a SKIP - a skip is how this stayed invisible. This lesson was then applied to itself: the census reader was branched to v3 rather than edited, and v2's bytes and v2's output were both retained.

## E-45 (2026-09-21) - A CHECK THAT WAS RUN AND NOT RETAINED IS A CHECK THAT WAS NOT RUN

The v5 method-record change table was verified against the document's section markers, by hand, in chat. It was correct. But the verification lived only in the conversation, so at v6 there was nothing to re-run, nothing to point at, and no way to show the v5 table had ever been checked. The evidence had the durability of chat, which is the weakest layer this campaign recognises. Cure: `check_method_record.py`, retained, bidirectional (every section the change table names must carry the version marker, and every marked section must be named), with a selftest that catches six tamperings. **The general rule: a check whose result is not on disk is a claim, not a check** - and obligation 12 now states that a gate never shown failing is not evidence.

## E-46 (2026-09-21) - THE PROPOSER, THE AUTHOR AND THE ORCHESTRATOR COLLAPSED INTO ONE VOICE

OW-17 amendment (c) requires that method-change proposals be adjudicated by an execution that is neither the proposer nor the orchestrator that ran the book. Under the budget ceiling the orchestrator wrote the five Ezekiel proposals itself, having also authored the deliverables they argue about. Three roles, one voice. What kept it from being silent: the collapse is written into the proposal file's own bytes, each proposal carries its own strongest reason to reject, and the proposals are **not** appended to the campaign log - the log is the owner's act after independent adjudication. The defect is real anyway, because self-disclosed non-independence is still non-independence. Two of the orchestrator's own evidence claims in those proposals were false and were caught only by re-measuring them before the file was written, which is the exact failure mode a separate adjudicator exists to catch. Cure: proposal adjudication is a SEPARATE execution, kept separate even when the budget is tight; when it cannot be, the close says the item is owed rather than met.

## E-47 (2026-09-21) - A READER DECIDED WHAT A ROW WAS BY STRING-MATCHING ITS SCHEMA NAME

The OW-15 census asked "is this row an attempt?" by testing whether the schema name ended in `_amendment.v1`. Eighteen rows of a new type, `m8_attempt_receipt_recovery_note.v1`, were then appended - each one a note ABOUT an attempt, carrying no execution id of its own. The census read all eighteen as fresh attempts with null execution ids and reported them as unmeasured-UNDECLARED, inventing eighteen undeclared attempts out of its own reading. The data was correct; the reader was wrong. Cure, as census v3: ask the **type-correct** question - a row carrying `amends_execution_id` amends another row and is never itself an attempt, whatever its schema is called. **A predicate keyed to a naming convention fails the moment a new name is correct**; key it to the field that carries the meaning. Detected and cured within the hour, and v2's bytes and v2's position file were retained so the earlier position stays reproducible.

## E-48 (2026-09-21) - A GOVERNANCE FLOOR THAT DEPENDS ON A RATE-LIMITABLE MODEL IS A FLOOR THAT CAN VANISH

The two blind lanes required to grade close-gate items 20-23 (OW-19: two lanes are the floor, and the orchestrator may not grade its own work) were launched and **both failed at launch** with HTTP 429, "out of usage credits", on model `claude-fable-5-1`. Measured immediately afterwards from the account's own usage card: the FIVE-HOUR window stood at 95 percent with a reset 2 hours out, while the weekly all-models window stood at 13 percent - so this was the short window, not the weekly exhaustion that stopped the 2026-09-16 lanes, and extra usage was disabled. Two consequences worth separating. **First**, the close gate cannot be graded at all until the window resets, and no amount of orchestration substitutes: an Opus lane auditing Opus-authored work is the same family and the same author, which OW-19 counts as one voice. The book therefore stays open with every non-Fable item finished. **Second**, both notifications reported status failed, carried **no usage block at all**, and named task output files measured at 0 bytes - the exact signature `ezek_ow15_residual.v1.json` attributes to the eighteen unmeasurable attempts. That was an inference about the past; it is now an observed property of this failure mode on this machine, and it means these two attempts are themselves unrecoverable spend, not zero. Cure: check the five-hour window before ordering a launch that a governance floor depends on, receipt a launch-time failure as an attempt (OW-7) rather than retrying it into invisibility, and never report a floor as met by a lane that did not run.
